# Публичный срез для аудита (демонстрационный)

Этот каталог **не является** полной копией производственного репозитория. Здесь **другие имена** файлов/модулей (префикс `audit_*.ts` и т. п.) и **плейсхолдеры** переменных окружения (`AUDIT_*` в примере конфига), чем в продакшене: это **не** «те же файлы, только без префикса». В продукте те же идеи лежат в **других путях и под другими именами**. Добавлен **осязаемый объём кода**, чтобы заявления о «открытом исходном коде» и модели «сервер не читает переписку» можно было **проверить глазами**, а не только README.

Что вы **можете** увидеть в коде:

- на **клиенте** — реальный вызов **Web Crypto API** (AES-256-GCM) для учебного слоя «шифрование до отправки»;
- на **сервере** — тип записи очереди **без поля plaintext**, guard отклоняющий JSON с открытым текстом, in-memory хранилище только непрозрачных blob;
- **ниже в этом же файле** — граница доверия: что серверу не положено хранить.

Чего **нет** (намеренно): полный прод-протокол, X25519/ratchet, WebRTC, реальные маршруты, схема БД, прод `.env`.

## Зачем другие имена

Публикация структуры каталогов и имён «один в один» упрощает целевые атаки (подбор конфигов, заголовков, путей). Поэтому:

- **Файлы в этом срезе** — учебные имена (`audit_…`), они **не соответствуют** прод-файлам по правилу «убрать `audit_` и получится прод». В продукте — своя раскладка модулей (например, криптография сообщений в других файлах, не копии этих).
- **Переменные в `env.sample.audit`** — только шаблон с префиксом `AUDIT_*`, чтобы не светить реальные имена переменных продакшена.
- **Маршруты и поля API** здесь обобщены или вымышлены.

Итог: срез показывает **класс решений**, а не карту имён боевого репозитория.

## Модель доверия (кратко)

1. **Сервер** — доставка и хранение **только** непрозрачных полезных нагрузок (шифртекст + служебные поля маршрутизации). Текст сообщения в открытом виде в модели не хранится.
2. **Ключи для чтения переписки** — на стороне клиента; сервер не реализует успешную расшифровку в этом срезе (`auditRelayDecryptPayload` специально бросает ошибку).
3. **Шифрование по умолчанию** — иллюстрируется тем, что HTTP-тело после клиента содержит только `sealed.ivB64` / `sealed.ciphertextB64`, а guard отвергает поля вроде `plaintext`.

---

## Граница доверия (что допустимо в этом срезе)

**Что «видит» транспорт.** В примере клиент формирует JSON с полем `sealed`: строки в base64 для IV и шифртекста, плюс ссылки маршрутизации (`targetRef` и т. п.). Открытого текста сообщения в ожидаемой схеме нет: попытка передать его под типичными именами (`plaintext`, `message`, `bodyUtf8` и др.) отсекается guard’ом на сервере.

**Что сохраняется.** Тип `AuditRelayQueueRow` и in-memory очередь содержат только идентификаторы/ссылки, время и непрозрачные поля `payloadCipherB64` / `ivB64`. Отдельного поля для хранения расшифрованного текста в типе нет — добавить «тихую» ветку «сохранить plaintext» без изменения типов и контракта не получится без явного нарушения модели.

**Расшифровка на сервере.** В учебном коде функция расшифровки с реле не вызывается; заглушка бросает ошибку. Это подчёркивает намерение: реле не является держателем ключей для чтения переписки.

**Оговорка.** Этот срез иллюстрирует **идею** и фрагменты API; полный прод-протокол (асимметрия, сессии, ротация ключей, версии) в репозитории намеренно не раскрывается.

## Как читать код (рекомендуемый порядок)

1. Разделы **«Модель доверия»** и **«Граница доверия»** выше.
2. `frontend/src/audit_default_crypto_web.ts` — что именно вызывается в браузере для seal/open.
3. `frontend/src/audit_client_send_flow.ts` — что уходит «на провод».
4. `backend/src/audit_incoming_guard.ts` + `audit_relay_schema.ts` + `audit_relay_memory_store.ts` — что допустимо сохранить.
5. `backend/src/audit_http_skeleton.ts` — склейка в одном обработчике.

## Сборка и проверка типов (опционально)

Файлы рассчитаны на чтение как текст. После `npm install` в `frontend/` и `backend/`:

```bash
npm run typecheck
```

в каждой из этих папок — проверка проходит без ошибок при Node 18+.
